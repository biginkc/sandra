# Bounded persistent Inbox projector

One PostgreSQL pool connection drives the same reviewed claim, canonical snapshot and fenced publication functions. Queries use independent autocommit statements: claim completion precedes source computation. No provider, action, or browser authority is accepted. The dedicated NOLOGIN role can execute ten named helpers and has no direct canonical table read/write grants. Credential provisioning remains a separate hosting operation.

The loop services historical baseline/backfill, parent fanout, expiry and up to25 summaries per round (configuration capped at100). Idle rounds wait one second; active rounds yield ten milliseconds. A failed or unexpected publication for one claimed item is caught, logged as `projection_item_failed` (identifiers only, never a payload) and counted; the claim is left to expire rather than retried immediately (bounded to one retry per 300s lease), and the round continues with the next item so one poisonous item cannot stall the whole projection lane. `/health` exposes the round's `poisoned` count. Pool/connection errors are not per-item and still stop the worker (see below); durable leases remain recoverable. SIGTERM finishes the active query, stops taking work and closes the pool. Health reports last successful round and bounded counts without reading payloads or querying the database per probe.

The package pins pg8.21.0 and the same Node22 image as the reviewed relay/action runtime. Pool max1 and asynchronous connection initialization follow the [node-postgres pool contract](https://node-postgres.com/apis/pool); every new connection sets the narrow role before use. Statement timeout is30seconds, lock timeout2seconds, connection timeout5seconds. TLS settings come from the deployment connection configuration and are not disabled in code.

This module can eventually share one worker image/process with the action loop while retaining separate credentials and pool1 (projection)/pool2 (action). That combined1CPU/1GiB service still needs its own integration/capacity proof. The current sidecar proof is isolated and has256MiB/.5CPU; it is not a production deployment or a production sizing result.

The independent sidecar is a local fixture proof. The hosting budget still permits one combined worker allocation of 1 CPU and 1 GiB, with separate action (maximum two connections) and projection (maximum one connection) pools. Combining supervision, shutdown and readiness with the signed action runtime remains a release requirement; this sidecar does not authorize a second production worker allocation.

A source review after the first live receipt corrected the idle-pool error path to exit nonzero for on-failure supervision. The existing persistent-image receipt predates that correction; rebuild and runtime failure/restart evidence must accompany activation of the changed source.

Production connections require a DNS hostname and certificate/hostname verification; weak SSL modes and arbitrary connection-string options are rejected. Plaintext is permitted only with `INBOX_PROJECTION_OWNED_FIXTURE_PLAINTEXT=true`, an exact approved loopback fixture endpoint, and matching expected database. The historical fixture uses loopback port5432 and its fixed database names. The disposable release HTTP fixture uses only `127.0.0.1:54322/postgres` and additionally requires the launcher to verify the `release-infra` owner, `sandra-inbox-release-http` purpose, and `sandra-inbox-http-owned-synthetic-20260917` marker before credentials are accepted. On every connection, the service verifies the original session login has safe role attributes, exactly the projection membership without administration rights, no effective direct table privileges (including SELECT), and no callable non-trigger SECURITY DEFINER routines outside the exact ten-helper allowlist. The audit includes inherited PUBLIC privileges. `SET ROLE` is not treated as a substitute for a constrained LOGIN. The actual fixture catalog probe passed; production credential provisioning is still unperformed.

The local first-start launcher has no restart policy. Transient database errors currently stop the process and leave claims to expire (maximum300seconds). Do not claim automatic recovery: the combined supervised worker must prove restart and stale-claim recovery before production enablement.
