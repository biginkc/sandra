# Private authoritative Inbox worker candidate

This candidate has passed owned full-schema signed runtime proof. Production deployment and the combined action/projection process remain disabled and unproved. It depends on the authoritative metadata SQL candidate and the installation baseline being complete.

The runtime uses Restate SDK 1.17.0 with the approved pinned Restate server 1.7.5. `server.mjs` registers `InboxMetadataOperation.run`. Each immutable accepted step runs in a durable `ctx.run` block and reconciles the retained SQL receipt on repeated delivery. Known policy conflicts finish as durable terminal results. The operation continues through unrelated properties, while failed dependent steps already have blocked receipts. SQL receipts retain idempotence beyond the engine response-retention window.

The dispatcher polls the durable acceptance outbox independently of browser lifetime, claims at most 20 rows with leases, sends each stable event ID as the Restate idempotency key, and acknowledges only after a validated durable acceptance response and a true SQL lease fence. A lost response leaves the outbox unacknowledged. Process restart resumes unacknowledged rows after lease expiry; Restate resumes accepted invocations from its durable log. Loss of the Restate durable store is not treated as an ordinary restart and requires a separate recovery plan.

The `/send` and `Idempotency-Key` conventions follow [Restate HTTP invocation documentation](https://docs.restate.dev/services/invocation/http). SDK endpoint `identityKeys` validation is verified against the pinned installed declaration at `@restatedev/restate-sdk/dist/endpoint/types.d.ts`. No unsigned callback mode is provided.

Startup requires `INBOX_ACTION_WORKER_ENABLED=1`, a database connection authenticating exactly as `inbox_action_worker`, one or two configured Restate signing public keys, and the approved private ingress hostname. Current exact candidates are `inbox-restate.railway.internal:8080` and the owned fixture alias `sandra-inbox-restate-owned:8080`. Hosting must match or explicitly revise this allowlist before launch. Database pool size defaults to 2 and cannot exceed 2. Readiness uses a single coalesced short cache, invalidates on dispatcher failure, and reports false until the authoritative baseline is complete and dispatch recently succeeded. Readiness remains a private endpoint. Container private networking and ingress controls are still deployment requirements.

`npm test` covers stable event identity, lost response no-ack, false acknowledgment fence, bounded response streaming, receipt replay, known-aborted SQL retry, ambiguous failure no eager retry, signed/private configuration, connection budget and readiness races. These unit checks are complemented by the actual signed runtime evidence described below.

The role installer also checks effective privileges, including inherited PUBLIC grants. It refuses any direct application table authority or reachable non-trigger SECURITY DEFINER function outside the five worker helpers. This audit must pass on the fresh full canonical schema; the lighter original fixture is not an ACL substitute.


## Actual owned runtime evidence

`runtime-evidence.json` binds seven completed groups to the exact source and built image: unsigned requests denied; real server-derived accepted outcome/assignment executes after the original Auth session closes; worker kill/restart and persistent Restate restart after the first canonical receipt; idle-engine outage/recovery and pool cap; real HTTP response destruction after durable acceptance, natural30-second lease expiry and PreviouslyAccepted same-event replay; and an actual prepare/worker deadlock where the worker reports40P01, retries the same immutable identities and emits one canonical event before Restate reconciles its receipt.

`fixture-install.py` compiles the reviewed metadata components with the production namespace transformation, verifies policy/Auth prerequisite bodies (including the rollout gate), installs once into the exact separate full-schema fixture and records source hashes. No canonical data or accepted jobs were copied. The role installer checks effective privileges including PUBLIC inheritance. `runtime-control.py` creates a new labeled pair only and refuses existing state; owner-only keys and connection configuration remain under ignored `.runtime-local/`. Runtime tests preserve the proof database and durable volumes. All seven groups used synthetic actors and SQL JWT claims; cryptographic browser authentication remains separately tested by the frontend harness. No providers were called.

The currently proven worker is separate from the projection sidecar. A final single1CPU/1GiB service must host action pool2 plus projection pool1 before production. The prepare/worker lock inversion is recoverable as proved, but ordering alignment remains a latency follow-up. The fixture runtime is not automatically restarted by Docker supervision; process restart was deliberately exercised by the proof. Production restart policy, operations monitoring and migration/release gates remain required.
