# Production authentication trigger feasibility — proposal, not verified deployment

The canonical fixture models auth.sessions as a postgres-owned subset, so its original trigger success did not prove production privileges. New read-only production metadata now shows postgres has explicit SELECT/TRIGGER while supabase_auth_admin owns the table. This supports testing the existing trigger design before pursuing an alternative. Do not change Auth ownership, ACL or RLS to make rehearsal pass.

Candidate alternative: maintain access epochs only from public.memberships, and query canonical auth.sessions live at every authorization boundary. Worksets already bind exact session ID and user ID. Session deletion or expiry is then rejected live, while membership revoke/restore and permission changes still bump durable membership epoch. This avoids invalidating a user's unrelated sessions when any session is created/deleted.

This is not yet proven equivalent. Without a session epoch, deleting and reinserting the same UUID, or shortening then restoring not_after between authorization boundaries, can revive an old scope. Current canonical Auth behavior and scope expiry fencing must be checked; never assume session IDs cannot be reused by privileged writers. One option is a persisted scope fingerprint of canonical session created_at and not_after, checked on every boundary; unchanged restored values still cannot prove intervening revocation. The production requirement must distinguish live session validity from historical irrevocable revocation.

Collected read-only privilege evidence includes: pg_class.relowner/relacl/relrowsecurity for auth.sessions, current_user, session_user, pg_has_role ownership, and has_table_privilege(current_user,'auth.sessions','TRIGGER') plus SELECT. The migration execution role must still match the observed postgres role; inspect the actual revoked-session lifecycle before changing authorization semantics. No secret session values are needed. After evidence, reproduce that role/ownership arrangement in a disposable fixture and run canonical auth/cursor/session revoke-restore tests. Preserve production Auth-table policies regardless of outcome.

Current bridge trigger stays unchanged until the alternate model is reviewed and adversarial tests pass. Production activation is blocked on this feasibility decision; the fixture is not authority to alter Supabase-managed Auth infrastructure.

## Actual read-only production privilege receipt

production-auth-privileges.json records postgres as current/session role, supabase_auth_admin as table owner, owner membership false, RLS enabled, force RLS false, no existing custom session triggers, and explicit postgres SELECT/TRIGGER privileges. Ownership difference alone therefore does not rule out trigger creation. No ACL or production DDL was changed. Next proof must reproduce these privileges and RLS in an isolated fixture table, create/fire the postgres-owned SECURITY DEFINER trigger as the Auth role, and test rollback without assuming ownership permits DROP TRIGGER.

Current Supabase docs explicitly recommend canonical session-row existence checks for sign-out guarantees, while time-box/inactivity cleanup is delayed; existence alone is not a complete timeout policy. See [session lifecycle](https://supabase.com/docs/guides/auth/sessions). Auth-trigger documentation describes postgres-owned SECURITY DEFINER functions for triggers fired by supabase_auth_admin; it does not establish every project's table privileges. See [Auth trigger troubleshooting](https://supabase.com/docs/guides/troubleshooting/dashboard-errors-when-managing-users-N1ls4A). Changelog scanned2026-09-13; relevant self-hosted Auth URL change does not alter this hosted schema proof.

## Equivalent privilege proof completed

auth-privilege-proof.py ran against a separate schema/table in the guarded fixture, with actual production role flags reproduced. Nonowner postgres CREATE TRIGGER succeeded. Auth-admin INSERT fired the postgres definer and wrote the private capture table even after direct function EXECUTE was revoked. Direct DROP TRIGGER was actually denied; postgres-owned function DROP CASCADE removed the trigger. The entire transaction rolled back, and the probe schema was absent afterward. No canonical Auth table was altered. This establishes a feasible installation/rollback mechanism without changing managed Auth privileges; migration-role identity and operational Auth impact remain deployment checks.
