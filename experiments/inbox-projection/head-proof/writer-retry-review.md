# Inbound-head writer and retry review

Source baseline: `c2b46ff6f45ada359e9b448b8d6682a2a94ae952`. Read-only repository review,2026-09-13. No application edits or database mutations. This is a bounded inventory of the named Inbox writers and identifiable SQL message writers, not a claim that every deployed integration or administrative session has been inspected.

## Conclusion

The source does **not establish automatic deadlock recovery for the existing Inbox writers**. The T2 proof demonstrated a valid row-before-head deadlock, but it used a controlled complete-transaction retry that production callers do not currently provide. Adding the capture trigger therefore requires error-preserving, idempotent retry work and real caller tests before production. A function named rollback in TypeScript is not a PostgreSQL rollback when it makes another HTTP request.

## Actual SQL and canonical trigger interactions

[`081_conversation_id_unify.sql:128`](../../../supabase/migrations/081_conversation_id_unify.sql:128) defines an ensure operation containing registry mint/upsert and a multirow messages UPDATE at164. The mint helper upserts `message_threads` at95–116. Registry and source/head locks therefore coexist in the same RPC transaction. The later Hugo wrapper calls the renamed original body in the same transaction at [`20260728150000_hugo_access_authorization_hardening.sql:688`](../../../supabase/migrations/20260728150000_hugo_access_authorization_hardening.sql:688). The current wrapper checks active access; do not evaluate only the older081 authorization text.

The canonical BEFORE fill trigger at [`081_conversation_id_unify.sql:180`](../../../supabase/migrations/081_conversation_id_unify.sql:180) mints registry identity when needed. A single inbound INSERT may therefore acquire registry locks before source/head capture. It still has one source INSERT, not the synthetic proof's explicit two-row UPDATE sequence; the proof does not establish identical deadlock frequency on this particular route. Concurrent registry backfill/restamp writers make ordering review necessary.

The migration's backfill DO block at [`081_conversation_id_unify.sql:224`](../../../supabase/migrations/081_conversation_id_unify.sql:224) loops over contact/property groups and updates messages repeatedly in one database execution. It has no explicit sorted group/row locking or deadlock retry. This is historical migration code, **not a recurring live worker or current assignment**. If its pattern is reused for repair/rebuild after capture exists, it needs bounded batches, a documented lock strategy, and whole-transaction retry.

Other identifiable SQL writers include property merge at [`067_merge_duplicate_properties_batch_scope.sql:68`](../../../supabase/migrations/067_merge_duplicate_properties_batch_scope.sql:68) and delete-contact at [`069_harden_destructive_rpcs.sql:44`](../../../supabase/migrations/069_harden_destructive_rpcs.sql:44), plus campaign cadence/queue controls. These functions perform multiple SQL operations in a single RPC transaction. Property-link, contact-link, read, status or scheduled-time changes alone do not change the candidate's org/conversation/channel/direction membership and do not necessarily allocate a head revision. They still acquire source/property/registry locks and remain relevant when raced with membership-changing writers. Do not assert every SQL message UPDATE becomes a new arrival or that every such function reproduces the demonstrated deadlock. The new guard also runs on general UPDATE, so privileged-owner compatibility must be checked even for non-arrival updates.

A repository search of non-test source/scripts/migrations found no40P01/deadlock_detected/serialization_failure handling in the reviewed application writers. Other modules use40001 for business stale-state/idempotency errors, for example [`workflow-actions.ts:59`](../../../src/lib/my-leads/workflow-actions.ts:59). Therefore “retry every40001 everywhere” is unsafe: distinguish actual retriable transaction aborts from explicit domain conflicts and preserve structured errors at the boundary.

## Privileged restore and bypass evidence

[`restore-sandra-cleanup-packet.mjs:263`](../../../scripts/restore-sandra-cleanup-packet.mjs:263) disables user triggers during a restore rehearsal and re-enables them at274. Its table groups at225–244 **do not include messages**. The entry point runs a serializable test transaction and rolls it back at343–350. This is evidence that privileged restore patterns exist, not evidence that this script currently bypasses the new messages capture or mutates production messages. Expanding its groups to messages later would need revision/head-aware restore semantics.

[`seed-jordan-training-rehearsal.mjs:45`](../../../scripts/seed-jordan-training-rehearsal.mjs:45) deliberately disables only the training guard in a disposable rehearsal to prove a missing-guard refusal; its finally block drops that test database. This is not a live production capture bypass.

No generic `session_replication_role` or `pg_restore` production path appeared in the bounded scripts/source search. That absence does not certify administrators, infrastructure restore tooling or external integrations. Superusers, the allocator owner, same-owner SECURITY DEFINER code, ALTER TABLE DISABLE TRIGGER and replication-role changes remain privileged exceptions. A restored source table and restored head counters must be treated as one consistent protocol state. Never restore messages at baseline0 or reset heads while continuing to accept old signed read boundaries. A backup/restore runbook must fence the new read path, invalidate prior boundaries/worksets as needed, validate/rebuild protocol state and then re-enable reads.

## Required work before production capture

1. Preserve SQLSTATE and operation identity through ensure/restamp/inbound errors. Add bounded, jittered retry at the **actual aborted database transaction boundary**, with an explicit maximum attempt/time budget and observable exhaustion. Do not retry only the last statement of a failed multistatement RPC.
2. Exercise real Supabase/PostgREST callers against injected40P01, lost acknowledgement and concurrent membership writers. Verify unique inbound event/message recovery, exact head counts, no duplicate domain/provider side effects and no false processed acknowledgement. Provider redelivery behavior remains independent evidence.
3. Replace silent resolve compensation failures with inspectable outcomes and revalidation. Decide whether resolve becomes one bounded command/RPC or retains a durable, explicit compensation design; do not call its current HTTP sequence atomic.
4. Establish deterministic source/registry/head lock ordering where practical and benchmark multirow backfill/restamp contention. Rehearse inverse order transactions and whole-transaction recovery; sorted caller IDs alone do not prove SQL executor row order.
5. Require final snapshot reads for new revision DTOs. Keep ordinary revision-forgery guards and revoked head privileges; inventory every privileged owner writer and restore path before widening rollout.
6. Set ingestion latency, WAL/vacuum and hot-thread contention budgets from representative workload. The measured write amplification and real deadlock remain production gates; this source review does not approve the trigger for deployment.
