## Separate projection dirtiness from command versions

Use the approved source-specific entity version namespaces; do not equate every summary update with a reply conflict. In one source transaction:

- Identity/content/policy mutations bump persistent relevant entity versions and dirty affected summaries. Message body/address/identity and conservative metadata changes advance command dependencies; read/status/timing display changes need not invalidate prepared reply content unless actual eligibility/content changes.
- Property status/outcome/owner/DNC/deletion/training/contact links and reply-template address fields advance their relevant namespaces. Contact consent/phone/name fields advance the relevant policy/content namespaces. Consent ordering changes and route-suppression policy changes advance policy versions. Review decision identity/status/disposition changes advance review/outcome dependencies.
- Read_at and dismissed-state display changes dirty summaries; dismissed_at also changes the approved unknown-action dependency. Presence and unrelated updated_at do not increment message-content versions.
- Retain counters through entity deletion/reinsertion. Use transactional row UPDATE/UPSERT counters, not a sequence as a commit watermark. Old/new tenant or identity keys must both remain distinguishable. These counters order one key, not all transactions globally.

Source truth is still canonical. The projection receipt commits only after a one-snapshot read of compute data, dirty generation G and projection revision R. Lock dirty then projection; reject stale R or regressed G; acknowledge only G even when a newer generation exists. Do not read/lock canonical rows, or add a canonical FK/trigger that does so, inside that commit lock section. The existing `projection-proof/setup.sql:76–96` rehearses this rule only for a smaller field set; its current message trigger is insufficient for the dependencies above.

## Bounded parent fanout without dropping children

A property can be shared by arbitrarily many conversation UUIDs. Never update every summary or build an unbounded child array inside the property's transaction. A parent dirty row stores persistent generation/ack, while a separate durable fanout job records `(entity kind,org,entity id,generation G,source-stream,cursor,claim generation)`. Batch size is an operational parameter to measure, not an approved latency/capacity promise.

Start with source-record cursors, not `SELECT DISTINCT conversation_id LIMIT N` over an unbounded history scan:

1. For a property, enumerate the message-link stream by `(property_id, id)` with explicit org verification, then the review-link stream by `(property_id,id)` with org verification. For a contact, enumerate message links by `(contact_id,id)` with org verification. Emit distinct conversation keys **within the bounded batch**, allowing safe repeated enqueues across batches. Checkpoint each stream independently.
2. Each batch transaction atomically inserts/increments child dirty rows and advances its durable cursor. Lock child dirty rows in consistent `(org,target kind,target key)` order. Use claim generation CAS so an expired worker cannot advance a newer worker's cursor. A crash after commit resumes from the recorded cursor; a crash before commit loses neither enqueue nor progress because both roll back.
3. On stream exhaustion, acknowledge only parent generation G after all streams have durable completion records. A newer parent generation stays pending and starts another pass. Never set ack to the parent's current generation merely because an older scan completed. Reuse progress while G is stable; a hot parent must not force a fresh pass on every batch.
4. A relationship created or moved behind the scan cursor must independently dirty both affected conversation/raw keys in the same source transaction. That direct capture is essential: the fanout scan is not a long-lived consistent database snapshot. A removed link also dirties its old key before disappearing. A restored/imported link bypassing capture invalidates this argument and requires repair, not a claim that keyset paging solved it.
5. Reconciliation provides an independent repair path. It cannot be the normal excuse for missing a source trigger or prematurely acknowledging a parent. Test interrupted parent jobs, inserts behind cursors, moved links, generation changes and overlapping workers before enabling a production worker.

For route suppression, ordinary message from_address/to_address indexes do not provide the exact normalized customer-route lookup required here. Two implementation choices require rehearsal: a separately maintained source-level reverse-edge table `(org,normalized route,message_id,conversation_id)` with index `(org,normalized route,message_id)`, or an expression/indexed canonical lookup matching the exact inbound-from/outbound-to normalization. The edge table must update transactionally on message insert/delete and org/direction/address/conversation/channel changes; omit canonical FKs to avoid unexpected commit-path locks. Do not normalize unknown group keys as a side effect. A backfill must fence/repair concurrent edge changes before relying on the edge for fanout. Scanning an entire tenant with regexp normalization inside a suppression trigger is unacceptable.

It is safe to over-enqueue historical/ineligible message links: the known compute resolves current window, property and latest contact. Reducing links to currently visible summaries alone is unsafe when a previously invisible conversation can enter the view. A published summary reverse index can be an optimization only after re-entry and missed-edge races are proved.

## Verified source constraints/indexes versus assumptions

These are migration-source facts, not a new live catalog attestation:

- `001_initial.sql:222–246` declares message UUID PK, nonnull created_at/status, contact/property FKs and separate nonunique property/contact/conversation indexes. Those single-column indexes do not prove efficient composite org-plus-source-ID keyset fanout.
- `20260815233000_leads_urgency_paging.sql:29–36` adds `(property_id,direction,created_at DESC)` and `(property_id,created_at DESC,id DESC)`. They serve other access paths; they are not evidence of an `(org,property,id)` enumeration index. Evaluate a narrowly justified message dependency cursor index rather than assuming all desired indexes exist.
- `20260828170000_messages_filter_timeout_hotfix.sql:9–25` indexes eligible known SMS by `(org,conversation,created_at DESC,id DESC)` with included contact/property/direction/read fields. It excludes queued/paused/contactless rows and is not a complete dependency reverse index or unknown-reader index.
- `007_consent_events.sql:39–42` supplies `(contact_id,channel,occurred_at DESC)` plus org. UUID tie ordering is still part of the query; exact composite ordered coverage needs plan verification.
- `20260624120000_sms_phone_suppressions.sql:28–35` guarantees unique `(org_id,channel,phone_e164)` and provides phone/org lookup indexes. This uniquely resolves a suppression row; it does not enumerate its affected conversations.
- `20260827110000_ai_disposition_reviews.sql:55–67` guarantees one review per source inbound message and one pending row per `(org,conversation)`; it also indexes pending lookups and property_id. This justifies the pending-review cardinality assumption, not arbitrary review-stream scan cost.
- `071_sendillo_rollout_schema.sql:74–87` guarantees a thread's `(channel,contact_id,property_id)` tuple and only **nonunique** conversation_id indexing. `081_conversation_id_unify.sql:29–33` adds contact-only uniqueness when property_id is NULL. These do **not** establish one thread row per `(org,conversation)`; current summary scalar output can error if the join multiplies rows. Detect/report such collisions before backfill, and decide an explicit repair/constraint policy rather than silently picking a thread row.
- The lab's t2_proof history/unread indexes are experimental objects, not evidence that the deployed schema has them. No route-edge or durable parent-job table exists merely because this document proposes one.

## Canonical trigger order and locks

`081_conversation_id_unify.sql:180–219` fills missing SMS identity in a BEFORE INSERT/UPDATE OF contact_id trigger. Capture finalized NEW in AFTER events, plus true OLD for departure. The head allocator performs a nested canonical message UPDATE; dirty capture must ignore revision-only self-updates and avoid publishing stale outer NEW. Compute later from canonical rows instead of materializing trigger tuples.

`20260830092331_switchboard_contact_preferences.sql:73–100` has a BEFORE contact trigger that can apply global-phone DNC flags. Compare actual resulting OLD/NEW flags even when the caller targeted a phone slot. Global registry is not read directly by this summary; its effects reaching contacts/properties must be captured there. A complete command-policy version design may additionally need the registry itself.

`20260827110000_ai_disposition_reviews.sql:96–153` updates pending reviews when property outcome changes. Both property-parent and review direct capture can occur in that one transaction. Duplicate dirty increments are safe; suppressing them with caller-settable flags is not. Existing DNC guards can reject contact/read writes (`20260815190000_true_dnc_property_lock.sql:95–145,401`); the failed source transaction must leave no dirty/version/edge changes committed.

Sorted multi-key dirty acquisition reduces avoidable lock inversion but cannot eliminate legacy source-row-before-head/dirty deadlocks. A property update already holds its source tuple and may update review rows; message writers may hold different source rows. Keep source triggers free of fanout reads and summary writes; document a global order for newly introduced private locks; require whole-transaction retry on deadlock/serialization failure in enabled writer paths. Do not claim deadlock freedom from sorted child keys alone. The approved projection commit must never acquire parent/source locks after locking child dirty/projection rows.

## Expiry and unknown identity mechanics

Known next_window_expiry derives from every recent eligible message, not just the latest. At `created_at +2160hours` exact equality remains eligible; wake strictly after the boundary (PostgreSQL1microsecond granularity), then recompute the full summary. Counts and chosen property can change before the last activity ages out. An old pending review can keep only the review view visible. Store/update expiry scheduling atomically with projection revision; a stale wakeup may safely re-enqueue but must not overwrite a newer deadline. Resume overdue jobs after restart and acknowledge/delete only the schedule revision claimed. No timers are scheduled for unknowns merely because known summaries expire.

Unknown capture requires persistent `(org,exact raw sender)->sender_group_id` mapping before stable typed targets can be published. Until this exists, internal raw-key dirty rows may support rehearsal but cannot masquerade as persisted action IDs. Retain the mapping/tombstone across empty groups if stable selection/receipt semantics require it; otherwise define an explicit generation/incarnation contract. Dismiss/restore acceptance must persist frozen eligible inbound-SMS/unmatched IDs; execution rechecks eligibility and never expands the raw group anew. Source legacy broad update helpers lack channel/direction restrictions (`triage.ts:425–451`); do not copy that breadth into new bulk commands.

## Actionable next implementation slice

Implement an isolated **message-direct capture plus identity registry** first: persistent known/raw-group dirty generations; exact raw-group typed mapping; actual OLD/NEW field comparisons; command dependency counters only for the approved relevant fields; and source-level edge representation needed by later fanout. Keep all objects private and outside production migrations. Prove insert, read/status change, body/route change, match/unmatch, SMS/channel transition, org/conversation/raw-key move, deletion/reinsert, nested arrival stamp and transaction rollback. Include equal timestamps and the already documented undefined legacy unknown tie behavior. Test concurrent new-group insertion and retained mapping identity, and assert no change to unrelated command versions.

Then add property/contact/review parent/direct capture and durable checkpointed fanout, using a property deliberately shared by many distinct conversations. Verify batches/checkpoints, crash/retry, parent G versus G+1, new/removed links behind the cursor, stale-worker fencing and both old/new organizations. Add route-edge backfill and consent/suppression fanout only when their indexed enumeration and race protocol are measured. Add expiry scheduling last against frozen as-of parity fixtures. This sequencing delivers independently reviewable units without pretending the current small projection trigger already covers all dependencies.

Before any rollout, enumerate privileged trigger-disable/replica-mode/TRUNCATE/restore paths and prove capture repair/cutover for them; a row trigger cannot detect its own absence. Current repository search and fixture proofs do not certify production admin/job/import behavior. Membership/access epoch invalidation remains a separate authorization plane: a correct summary is not sufficient permission to read it.
