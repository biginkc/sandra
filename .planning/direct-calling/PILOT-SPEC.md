# Direct calling pilot — build spec (orchestrator-owned)

Owner decision (Jarrad, 2026-10-01): the softphone must stop going through Jitter. Morning goal: Jarrad, and only Jarrad, places a call from Sandra's existing softphone straight through Telnyx and checks the audio is clear. Every other user is unchanged.

Scope is deliberately small. **In:** pilot gate, browser registration, server-dialed browser leg, server-dialed seller leg bridged on answer, status, hangup, mute (local), hold (SDK), DTMF (server), wrap-up through the existing path. **Out:** coaching, recording, mid-call recovery, Railway worker, min-build gate, Dialpad, any Jitter deletion. Jitter path stays exactly as is for everyone not in the pilot.

## Call flow

1. Softphone opens (pilot user) → `getDirectRtcToken()` → server ensures the user has a Telnyx telephony credential on the Sandra browser connection (one per user, stored in `direct_call_operators`), mints a JWT, returns `{ token, sipUsername }`. Browser registers with `@telnyx/webrtc` 2.27.1.
2. Rep clicks call → `startDirectCall({ propertyId } | { phone }, clientRequestId)`:
   - authenticates; requires pilot membership;
   - runs the **existing** `prepareLeadCall` / `prepareManualCall` unchanged (DNC, quiet hours, training, enrollment pause — no rule logic is copied or altered);
   - refuses if the user already has a non-terminal direct call;
   - inserts `direct_calls` (status `browser_connecting`, frozen destination + caller ID);
   - Telnyx Dial to `sip:<sipUsername>@sip.telnyx.com` from the caller ID, `client_state` = base64 `{"directCallId","role":"browser"}`, `custom_headers` `X-Sandra-Direct-Call-Id`, `timeout_secs` 30, `time_limit_secs` 7200, `command_id` = a fresh UUID stored on the row;
   - stores the browser leg `call_control_id`; returns `{ directCallId, browserLegId }`.
3. Browser: on incoming invite, auto-answer **only** if `call.telnyxIDs.telnyxCallControlId === browserLegId` OR the `X-Sandra-Direct-Call-Id` header equals the pending `directCallId`. Anything else is rejected, never answered.
4. Webhook `call.answered` for the browser leg → if the row is `browser_connecting` and was created < 60s ago → Dial seller: `to` = frozen destination, `from` = caller ID, `link_to` = browser leg, `bridge_on_answer=true`, `bridge_intent=false`, **no** `park_after_unbridge` (no recovery: browser loss ends the seller leg), `timeout_secs` 30, `time_limit_secs` = 7200 − elapsed, `client_state` role `seller`. Status → `seller_dialing`.
5. `call.answered` seller → status `connected`. `call.bridged` recorded.
6. `call.hangup` on either leg → hang up the other if live; status `ended` (or `failed` if the seller never answered) with `hangup_cause` saved.
7. Browser polls `getDirectCallStatus(directCallId)` every 1s while active.
8. Wrap-up uses the existing `completeSoftphoneCall` **unchanged**, through the sealed capability: the same call capability the Jitter path mints, bound to `directCallId`, so it writes `provider='sandra_softphone'`, `jitter_attempt_id='sandra-<directCallId>'`. No change to `call_activities`, reconciliation, training checks or recording routes.

## Teardown and operator lock

- Every provider-side cleanup obligation is a row in `direct_call_cleanups`, never a column on the call: a `leg` row (hang the leg up until confirmed) or an `unresolved_dial` row (a browser or seller Dial whose outcome is unknown; written BEFORE the Dial, in the same transaction as the state change: the call insert in `direct_call_begin`, or the transition to `seller_dial_state='pending'`).
- **Operator busy** = a non-terminal `direct_calls` row OR any unconfirmed cleanup row. It is enforced atomically in `direct_call_begin` (advisory lock per operator; the partial unique index on non-terminal calls is a second fence). `startDirectCall` reserves the call there BEFORE running prepare, so prepare (which pauses lead enrollments) only runs for an allowed call.
- **Leg confirmation** is only: the leg's `call.hangup` webhook, a hangup refusal of 422 with code 90018, or `GET /v2/calls/{id}` `is_alive:false`. A 2xx hangup is "accepted" only (re-checked no sooner than 10s, re-sent with a fresh command id if still alive); a 404 or any other 422 confirms nothing.
- **unresolved_dial** resolves when the Dial returns/learns its leg, the provider refuses it (4xx), a webhook with this call's `client_state` reveals the leg, or reconciliation proves none exists: `GET /v2/connections/{app_id}/active_calls` (cursor paginated, matched on `client_state`) shows no match in two consecutive complete listings at least `timeout_secs`+15s after the attempt. A match becomes a `leg` row and is hung up. Backstop: attempt + `time_limit_secs` + 60s (logged `resolved_by_time_limit`).
- **Backoff**: every attempt (success, failure, 429, error) sets `next_attempt_at` (5s doubling to 60s, upward jitter, honouring `Retry-After`). Rows are claimed atomically, **one at a time, immediately before each is worked** (45s lease; one row costs at most a hangup plus a status request at 10s each), so provider traffic per row does not depend on how many polls, webhooks or tabs trigger processing and a slow earlier row cannot let a later row's lease lapse. Triggers: webhook, status poll, start, explicit hangup. Every 4th consecutive unsuccessful hangup attempt on a leg (any non-2xx other than 422/90018) also does a GET, so `is_alive:false` can confirm a leg whose hangup keeps failing.
- **Teardown obligations are decided in SQL, not from a snapshot.** When `direct_call_apply` moves a call to `ending`, `ended` or `failed` it takes the row lock and queues a `leg` cleanup for every leg id on the CURRENT row that has no evidence of having ended (an existing cleanup row, or a received `call.hangup` event for that leg); open `unresolved_dial` rows are never touched by that move. This closes the race where a hangup handler read `seller_leg_id=null`, a concurrent seller Dial response stored the leg, and the handler's status-only update then went terminal with a live seller.
- A webhook answers 200 once its event and any cleanup rows are committed; 500 only when that commit fails.
- Late or conflicting legs (for example an old call's late event while a newer call is live) are simply `leg` rows: nothing is forgotten and nothing is refused.
- `DirectCallStatusView.cleanupPending` is derived from unconfirmed cleanup rows; a terminal status with `cleanupPending=true` is not authoritative for the browser.
- No seller Dial is issued once teardown has begun (`ending`, terminal or `teardown_pending`), and a persisted `seller_dial_state='pending'` with no seller leg is an unknown outcome (call fails `dial_outcome_unknown`; never re-sent).
- `cancelDirectCallByRequest(clientRequestId)`: a call exists for the id, then the normal hangup path; none, then a terminal tombstone (`failed`, `cancelled_before_start`) so a late `startDirectCall` with that id returns `cancelled` and dials nothing. `getDirectCallStatusByRequest` polls by request id.
- Lead pause: prepare pauses a lead's enrollments (existing logic). When a lead call becomes terminal without having connected, `direct_call_apply` sets `direct_calls.resume_pending` in the same write, only if no other non-terminal direct call is on the property (a connected call's resume stays with wrap-up and never sets it). The webhook cannot resume: `resume_sequence_enrollment` refuses a service-role caller acting for a user (`not_authorized`), and that RPC is unchanged. The flag is worked ONLY from the operator's own authenticated server actions (`getDirectCallStatus`, `getDirectCallStatusByRequest`, `startDirectCall` before reserving, `controlDirectCall` hangup): claim with a 30s lease, re-check that no other direct call has taken the property (if one has, the flag is cleared without resuming: that call owns the pause), call the existing `resumeFailedSoftphoneCall(propertyId)` unchanged, and clear the flag only if it returned without throwing. `resumeFailedSoftphoneCall` swallows every error and returns `void`, and `resumeByProperty` ignores a non-`resumed` RPC outcome, so a refused or failed resume is **not visible** to the direct-calling code; those functions are intentionally not changed. If the browser never returns after a webhook-driven failure, the existing stuck-call sweeper is the backstop (same as the Jitter path today). Known limits (same as the Jitter path): the 30-minute stuck-call sweeper can resume a pause under a call that runs longer; a crash between prepare and the target being stored leaves the pause to that sweeper.
- `startDirectCall` errors carry `reserved`: `false` is a proven pre-reservation refusal (`not_enabled`, `invalid_request`, `cancelled` tombstone, `call_in_progress`, `teardown_pending`, a precheck failure, or a prepare refusal whose reservation was discarded); anything else (`true`, absent, or a lost response) means a reservation, a Dial or cleanup may exist, and the browser reconciles by request id and treats the start as finished only at terminal + `cleanupPending:false`.

## Rollback

Removing the pilot env vars (`DIRECT_CALL_PILOT_USER_IDS` and the `TELNYX_DIRECT_*` set) disables new calls. Before removing `TELNYX_DIRECT_API_KEY`, drain live calls: without the key the server cannot hang up legs, so confirm no direct call is live (and no `direct_calls` row has a pending hangup) first.
