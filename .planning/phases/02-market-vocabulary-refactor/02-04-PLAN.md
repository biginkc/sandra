```sql
-- 045_backfill_property_county_id_from_fips.sql
--
-- Phase 02 — Market Vocabulary Refactor (per CONTEXT.md D-05).
--
-- Backfill properties.county_id (and properties.market as the synced cache
-- per D-04) for existing rows. Two source signals, applied in order:
--
--   Step 1: properties.fips_code -> counties.fips_code (JOIN)
--           Expected ~{N1} rows (verified by plan 02-04 Task 1).
--   Step 2: cass_raw_response[0].metadata.county_fips -> counties.fips_code
--           Expected ~{N2} rows.
--
-- Properties with neither signal (~{N3} rows) are LEFT ALONE per D-05 -- they
-- retain market='Kansas City' and county_id=NULL until next CASS verify
-- catches them. Per D-09 there is NO catch-all "Kansas City" county row.
-- Outliers (TX/CA/CO test data) naturally fall through the JOIN with no match.
--
-- Idempotent: each step's WHERE clause includes `p.county_id IS NULL` so
-- re-running the migration is a no-op for already-backfilled rows.
--
-- Atomic: wrapped in BEGIN/COMMIT -- partial failure rolls back.
--
-- CI-only: applies on PR merge via .github/workflows/db-migrate.yml to both
--   - prod (copflsklaefwzipsrjqz)
--   - test (ncsngxlcyxylaeskiteu)

begin;

-- 1. Backfill from properties.fips_code -> counties.fips_code.
--    The JOIN is the canonical path: ~1,149 rows on prod (per CONTEXT D-05).
--    counties.fips_code is unique-where-not-null (index from 043) so the
--    JOIN cardinality is at-most-one-county-per-property -- no duplicate
--    UPDATE rows.
update properties p
set county_id  = c.id,
    market     = c.market,
    updated_at = now()
from counties c
where c.fips_code = p.fips_code
  and p.fips_code is not null
  and p.county_id is null;

-- 2. Backfill from cass_raw_response jsonb fallback.
--    Targets ~26 rows (CONTEXT D-05) that have a CASS response but no
--    properties.fips_code populated. Reads element [0] of the jsonb array
--    (most recent verification) and pulls .metadata.county_fips out as text.
--    Same idempotent gate (county_id IS NULL).
update properties p
set county_id  = c.id,
    market     = c.market,
    updated_at = now()
from counties c
where c.fips_code = (p.cass_raw_response->0->'metadata'->>'county_fips')
  and p.fips_code is null
  and p.cass_raw_response is not null
  and p.county_id is null;

-- 3. INTENTIONAL NO-OP: properties with neither fips_code nor a CASS county_fips
--    keep market='Kansas City', county_id=NULL. Per D-05 + D-09 these resolve
--    naturally on next CASS verify of each property. DO NOT insert a synthetic
--    Kansas City county row to "catch" them -- that re-introduces the legacy
--    enum we are trying to delete.

commit;
```

Replace `{N1}`, `{N2}`, `{N3}` with the actual row counts from Task 1.

DO NOT add a Postgres trigger to keep market in sync with county_id. Per D-04 the sync is application-layer (csv/ingest.ts + leads/create.ts updated in plan 02-03). A trigger would be invisible behavior.

DO NOT widen step 2 to also touch rows that already have county_id set — re-running on a corrected county would silently overwrite. The IS NULL gate is critical.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-04-01 | Tampering | properties.market mass UPDATE | mitigate | UPDATE is constrained by the JOIN on counties.fips_code — only properties whose fips_code matches a seeded county are touched. The unique index `counties_fips_code_unique` (from 043) guarantees at-most-one-county-per-fips, so no row is double-updated. |
| T-02-04-02 | Denial of Service | row-locking on the properties table | mitigate | Migration runs once at deploy time on a 2,533-row table — UPDATE completes in well under a second on Supabase Pro. BEGIN/COMMIT transaction is short. No production traffic impact expected. |
| T-02-04-03 | Repudiation | who set which county_id when | mitigate | The migration sets `updated_at = now()` on every touched row, providing a clear audit timestamp. schema_migrations records the version + applied_at. |
| T-02-04-04 | Tampering | re-run silently overwrites corrected county_ids | mitigate | The `WHERE p.county_id IS NULL` gate makes both UPDATEs no-ops on rows that already have a county_id. Manual corrections after the migration are NOT clobbered by re-runs. |
| T-02-04-05 | Information Disclosure | jsonb path traversal on cass_raw_response | accept | The `->0->'metadata'->>'county_fips'` path is read-only and operates on the row's own jsonb. No cross-org data exposure possible — UPDATE remains bound by the WHERE clause and Supabase Pro's RLS posture. |
| T-02-04-06 | Tampering | partial failure leaves properties partly updated | mitigate | BEGIN/COMMIT wraps both UPDATE steps; an error in step 2 rolls back step 1's changes. CI surfaces the error so the PR can be reverted. |
</threat_model>
