### Server-side validation (T-02-03-01 mitigation)

- `createImportJob` queries the counties table for `params.countyId` BEFORE any insert. If no row (or RLS-rejected), returns `{ ok: false, error: { code: "INVALID_COUNTY", message: "Invalid county" } }` and writes nothing.
- The market string used for csv_imports.market / jobs.input_params.market / workflow start params is `county.market` (server-derived), NEVER `params.market` (client-supplied).
- Unit tests cover: happy path (counties queried first), canonical-market reconciliation, INVALID_COUNTY on unknown id, INVALID_COUNTY on RLS-reject error shape, countyId in workflow start payload.

### Defensive recovery in workflow body

```typescript
let countyId = params.countyId;
if (countyId === null) {
  const supabase = createAdminClient();
  const { data: row } = await supabase
    .from("csv_imports")
    .select("county_id")
    .eq("id", params.csvImportId)
    .single();
  countyId = row?.county_id ?? null;
}
```

Hot path (jobs queued after this plan ships): `params.countyId` is non-null, no DB read. Cold path (legacy retries / jobs queued before this plan): `params.countyId` is null, recovery DB read fires and threads the persisted value down. Both branches verified by unit tests.

## Decisions Made

1. **Hand-patched supabase/types.ts.** Migrations 043+044 ship via CI on merge — types would be regenerated then. But the plan ships application code that writes `csv_imports.county_id` and `properties.county_id` BEFORE the type regeneration runs. Without the hand-patch, every county_id write would fail typecheck and gate the PR. The hand-patch faithfully transcribes the migration's column additions + FK relationship; will be regenerated cleanly on next supabase types run.

2. **Server-side reconciliation pattern.** The wizard sends both `market` (string) and `countyId` (uuid). The action distrusts both — it queries counties for the supplied id and uses `county.market` for everything downstream. The wizard's market string survives only as a soft breadcrumb (it's never compared to anything authoritative). This collapses the trust boundary from "client picks any string" to "client picks a row id, server picks the string".

3. **Required, not optional, countyId on ingestRow.** The Plan's interface block says ingestRow signature gains `countyId: string | null` as a required positional. I implemented it that way (not as `?: string | null`) so callers can't silently drop it. The legacy `runIngestion()` path threads `params.countyId ?? null` to keep existing integration test fixtures working.

4. **Defensive recovery in workflow body, not in processChunkStep.** Resolution happens once at the top of the workflow body. The chunk loop receives the resolved id. This avoids re-querying csv_imports on every chunk for every retry — single DB read, cached in workflow state for the rest of the run.
