## Revision 2 — resolves Fable B1–B4 and R1–R5

These concrete choices supersede deferred alternatives above.

### HTTP responses and receipts (B1)

Invalid/stale signatures return 401; oversized body 413; malformed envelope 400. Signed valid irrelevant events, feature-off, unsupported links, policy denials and duplicates return 200 no-op, not errors that induce Slack retry storms. For recognized accepted work, commit durable enqueue before 200; only transient persistence failure returns 503 within the three-second deadline. Store sanitized denial categories on existing receipts when available; a denied event must not acquire a 5xx response solely because denial logging failed. Never persist rendered content. Lifecycle revocation events remain handled even when the preview flag is off. Endpoint tests assert all denial status codes, durable-enqueue failure and duplicate receipts.

### Named worker and guarantees (B2)

Implement an authenticated `/api/cron/slack-unfurl-sweep` endpoint wired in `vercel.json` at `*/1 * * * *`, using the repository's existing CRON_SECRET verification. Add a dedicated `slack_unfurl_jobs` outbox through the established migration workflow rather than reusing Norma's notifications table. Unique `(team_id,event_id)` receipts and per-URL delivery state; indexes for due work. An SQL RPC uses `FOR UPDATE SKIP LOCKED` to atomically lease due jobs with a unique claim token, a 90-second lease and token-fenced completion/backoff writes. Worker execution budget is 45 seconds, SDK request timeout 5 seconds with internal retries disabled; abort work before budget/lease expiry. Only one live claim may execute per job. Reclaim after lease expiration; cap attempts at five and event age at 15 minutes based on validated event_time. Expired jobs are abandoned without disclosure. Backoff is 15/30/60/120 seconds, respecting Slack Retry-After only within TTL. Optional after() kicks the SAME claim worker after persisted enqueue for low latency; cron provides durability and retry recovery.

Delivery is at-least-once, not an impossible exactly-once external-call guarantee. Two concurrent live workers must produce one chat.unfurl call; a crash or bookkeeping failure after Slack success may repeat the call to the same original URL/channel/ts, which Slack updates instead of creating duplicate cards. Revalidate authorization on every dispatch attempt, including recovered claims. Handle per-URL successes without repeating unrelated successful URLs. Preview data is a snapshot read during processing, not reconstructed historically at event_time. Retain identifier/status-only receipts seven days and clean through this worker; no tokens, excerpts or full rendered blocks in jobs/logs.

### Channel policy and scopes (B3)

Request channels:read and groups:read in addition to link scopes. Store approved team/channel/org tuples and an explicit operator sharing-policy acknowledgement. Before each delivery, use conversations.info with that exact installation token and require channel ID match, a channel/group type, no DM or group DM, no archived/shared/external/org-shared/pending-shared state, and authoritative evidence tying the channel to the expected workspace. Missing required evidence, errors, or rate limits deny the current attempt without disclosure (transient rate limits may be retried within TTL). Keep bot channel membership as a setup gate. Subscribe to supported channel_shared lifecycle events after checking current Slack event schema; revoke matching approval when a channel becomes shared. Runtime conversations.info is mandatory regardless of lifecycle delivery. Operator acknowledgement explains that Slack retention, notifications, search, forwarding and digests can expose excerpts beyond the immediate channel view. Channel approval is a deliberate sharing authorization, not an assertion that an internal channel's members inherently have CRM access. No automatic channel enrollment.

### Revocation (B4)

Subscribe to app_uninstalled and tokens_revoked and process signed events durably against the exact team/app installation, with correct token/user revocation granularity from Slack's schema. Revoke installation or affected authenticated identity as appropriate, cancel pending jobs and invalidate approval; do not revoke unrelated installations. Treat invalid_auth/token_revoked/account_inactive API responses as terminal identity/token failures, stop retries and require reconnect. Reconnection creates a new installation version so old jobs cannot resurrect. Worker checks current installation version/status, active linked membership and current channel approval immediately before sending. Tests cover revocation, reconnect, delayed jobs and feature-off lifecycle processing.

### Remaining precise rules (R1–R5)

- Strict URL acceptance: HTTPS, exact lowercase canonical Sandra host, no userinfo or explicit ports; `/leads/<uuid>` accepts irrelevant query/fragment for lookup, `/my-leads` requires exactly one valid lead query value. Other query/fragment content never influences authorization or destination. Preserve the original URL string only as Slack's unfurl map key; button URL is newly constructed from the validated identifier and trusted origin. Reject deceptive paths/hosts and ambiguous lead parameters. Cap links at five per event; over-limit signed events return 200 no-op with no disclosure.
- Login continuation accepts only validated same-origin relative paths; test absolute and protocol-relative redirect attempts.
- Poster identity must come from an authenticated account link bound to workspace/app and an active Sandra membership. Check Slack users.info with the existing users:read scope to deny bot/deactivated users. Do not match email addresses as an authorization shortcut. Missing identity evidence denies.
- Format times in the organization's configured timezone with a documented America/Chicago fallback if absent. Logs contain only sanitized codes and IDs. Seven-day job cleanup is part of acceptance.
- Implementation sequence starts with tested selected-lead deep linking, then installation/policy/outbox, signed ingestion and worker, pure renderer/data loader, and integration/canary. The existing privacy and flag-off release gates remain.

Tests specifically include concurrent claims, abandoned leases, Slack success plus DB-write failure, no-op denial responses, lifecycle events while disabled, live shared-channel transitions and token revocation. No claim of exactly-once delivery, historical snapshots, or immediate previews when only cron recovery is available.

## Revision 3 — Fable residual findings

These choices supersede Revision 2 where applicable:

1. Receipt and enqueue are one atomic SQL RPC transaction: insert unique team/event receipt and associated message job together, rolling back both on failure. A duplicate receipt is acknowledged only if its durable job exists or it is a terminal no-op. Never record a success receipt before enqueue. If an inconsistent legacy receipt exists, repair/enqueue transactionally rather than swallow its retry. Test injected job-insert failure after receipt insertion, full rollback, and successful re-enqueue on Slack retry.
2. The delivery unit is the whole posted message. Each attempt sends one chat.unfurl call with the complete map of currently authorized/resolvable supported URLs from a fresh snapshot. Per-URL state stores lookup/authorization results only, not partial delivery. A successful call completes the message job; a transient failure retries the whole map. Retry tests assert all eligible URL keys remain present. For duplicate event IDs/message events and recovered jobs preserve canonical message targeting; never treat external delivery as per-URL exactly-once. If all URLs are denied/unavailable, finish as a no-op. Snapshot and at-least-once semantics stay unchanged.
3. Explicit account-link flow: initiated by a signed-in Sandra user choosing an active organization they are authorized to use; OAuth state is signed, expiring and single-use, bound to Sandra session user, org and flow purpose. Callback rechecks authenticated user and active membership, exchanges code, stores Slack-returned team_id/app_id/authed_user.id and Sandra user/org atomically with encrypted bot-token installation version. Refuse absent/ambiguous identity or mismatched installation app. Existing links without verified team/app/user/org provenance, including email-derived mappings, have no preview authority until this flow is repeated. Email is never used for binding. Test callback identity/session/org mismatch, replay/expiry, missing returned IDs, cross-org link and reconnection version changes.
4. Deployment must prove the configured Vercel plan supports and actually executes the one-minute cron before enabling previews. Canonical CTA is `/my-leads?lead=<lowercase UUID>`; strict posted paths have no trailing slash, and IDs accept case-insensitive valid UUIDs then normalize for internal lookup. Login continuation remains same-origin only.
