## Fixed test contracts and scope
Tests exercise actual enrollment/tick/send/inbound application paths, real PostgreSQL/PostgREST and the actual unique enrollment/step constraint. Only external provider transport/clock and targeted failure boundaries are controlled. No mocked state machine or alternate claim query.
- Happy path: SMS A delay 0, SMS B delay 10 minutes, nonterminal status change delay 10 minutes. Correct order/recipient/body/sender/opt-out suffix, exact app-scheduled due times, durable step/message links, and final completed state; no work before due and no sends after completion.
- Duplicate prevention: synchronized concurrent ticks of one due step produce one provider invocation and one durable claim, plus a separate enrollment positive control. Count actual invocations, not unique provider IDs (the built-in mock reuses deterministic IDs).
- Stop boundary acceptance: a committed reply/pause/cancel/STOP prevents every submission not yet authorized. The sole permitted in-flight exception is the final authorization DB read/transaction already started before the stop commit. That authorization must jointly examine current enrollment state and applicable contact/property/phone suppression, be the LAST awaited operation before calling the provider, and have no intervening awaited work or DB operation. Instrument the operation trace and assert this structure; suppression alone without enrollment state is insufficient. Stops committed before the authorization read starts must yield zero submissions. Cover commits during the authorization transaction, immediately after it resolves, and inside an already-entered provider call; only that one authorized attempt may settle and no future step may fire. Post-send advancement must not overwrite a later stopped state. This is an explicit bounded operation-order contract, not a zero-time atomic external-send guarantee. Existing missing rechecks or intervening awaits produce failures.
- Mandatory no-stall acceptance: after a definitive rejection and separately a crash-after-claim, run two more due ticks and inspect persisted enrollment/run/message state. It must either expose an existing successful explicit recovery operation or a durable user-visible terminal/failed/paused-actionable state explaining why progress stopped. A retained claim with an active due enrollment, no possible progress and only a historical skip marker FAILS, even if later ticks return HTTP 200. An actionable pause passes this no-silent-stall check only; the separate explicit recovery test must still pass for recoverability to be claimed.
- Recovery acceptance: definitely-not-sent failure corrected by an operator must be able to progress through explicit existing resume/recovery behavior, with one accepted SMS and audit trail; ambiguous/accepted attempts must never be blindly resent. If no suitable recovery operation exists, emit an explicit unmet-contract failure and a proposed-fix finding; do not implement a new recovery policy as part of test work. No automatic retry schedule for native sequences.
- Existing archive/deactivate semantics are characterized as preventing new enrollments while allowing existing ones. Mid-flight edits are characterized, not approved as safe. These characterization cases never satisfy release acceptance.
- No waiver of duplicate sends, missing suppression, cross-tenant sends, false completion or silent permanent stalls. A known bug may be demonstrated by an expected-failure fixture only if a separate mandatory acceptance summary still exits nonzero. No xfail-to-green reliability claim.
